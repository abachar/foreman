# Architecture, concurrency and memory audit — 2026-10-17

Read of the codebase (~28,400 lines, after M22) on three axes asked by the author: main-actor isolation
against a 120 Hz budget (8.33 ms a frame), the Swift concurrency model, and the memory footprint. Every
finding is tied to a file and a line as they were on `main` 4fd3c82; the terminal findings also read
SwiftTerm's own sources (`DerivedData/SourcePackages/checkouts/SwiftTerm`). No code was changed.

The audit was then **sized against a real workspace**, the author's `ccoe` (four repos, two to three
agents at a time). Those numbers decide which findings matter and which do not; they are in §5, and
each finding below says what they do to it.

Finding ids: `U*` main actor, `K*` concurrency, `M*` memory. The fixes are tracked in
[M23](../backlog/m23-performance.md).

## 1. The frame the code is read in

- **MainActor isolation by default** (`coding-rules.md` → Toolchain). Everything that is not
  `nonisolated`, an `actor` or `@concurrent` runs on the main actor. What is explicitly taken off it:
  five actors (`GitCLI`, `FSWatchService`, `QuickOpenIndex`, `SelectorIndex`, `PostgresClient`), a
  dozen `@concurrent static func` for disk reads, parsing and the diff render (`FileDocument.read`,
  `DirectoryLevel.read`, `GitDiffModel.fetch/render`, `GitFeature.loadStatus`, `EditorTab.structure`,
  `WorkspaceState.load/write`, `Highlighter.build`), and `PipeIO` on `DispatchIO` with a `Mutex`.
- **Data crosses to the main actor as immutable `Sendable` values** (`GitStatus`, `DirectoryLevel`,
  `FileDocument`, `RenderedHunk`), installed into `@Observable` models.
- **Notifications are `AsyncStream` fan-outs** produced and consumed on the main actor
  (`TerminalService.events()` :46–54, `GitFeature.statusChanges()` :312–320,
  `Workspace.configChanges()` :91–99, `FSWatchService.changes(under:)` :36–45), default unbounded
  buffering. Debounce is at the producer everywhere (FSEvents 300 ms with a 1 s ceiling, state 1 s,
  LSP `syncDelay`, folds 300 ms, search 50 ms, scratch 1 s).
- The August audit's findings on this ground are closed and verified here: the two editor retain
  cycles (C1 — `Coordinator.tab` is `weak`, `EditorTextView.swift:239`; `tabClosed` drops the
  coordinator, `EditorFeature.swift:324`), the diff rendered on the main actor (M3b — `render` is
  `@concurrent`, `GitDiffModel.swift:196`), the gutter's O(document) draw (M3e — `lineStarts` cached),
  the search updated per match (M22 22.4). One is still open: M15, see U6.

**Verdict.** The architecture is sound and the concurrency rules are followed. There is no contention
problem. The two real subjects are (1) the terminal emulator's VT parsing, which SwiftTerm runs on the
main thread and Foreman leaves there, and (2) derived values recomputed on the main actor at a
frequency the data size does not justify. The memory bottleneck is the terminal scrollback, a
deliberate choice (terminal R14); the one memory finding worth a change is the diff rendered whole.

## 2. Main actor and the 8.33 ms budget

### U1 — The terminals' VT parsing runs on the main thread, 4 ms a slice

`TerminalSurfaceView` is a `LocalProcessTerminalView` with default options
(`Terminal/TerminalSurfaceView.swift:20`). SwiftTerm's `LocalProcess` takes
`dispatchQueue ?? DispatchQueue.main` (`LocalProcess.swift:127`), reads the PTY on its own
`readQueue`, then `drainReceivedData()` calls `delegate.dataReceived` — the whole VT parse and buffer
mutation — **on the main queue, in slices of `pendingTimeSliceNs = 4 ms`**
(`LocalProcess.swift:91, 163–207`), with back-pressure at 4 MB / 1 MB. Rendering is coalesced
(`queuePendingDisplay`, `AppleTerminalView.swift:2522–2535`).

*Why it holds:* it is the library's model (`Terminal` is not thread-safe), Foreman adds no per-byte
work, and the 4 ms slice plus back-pressure are real guards. *Where it breaks:* one chatty surface
takes half the frame; two agents streaming at once can fill a frame before the editor draws a pixel.
**ccoe: two to three agents at a time — this is the nominal case, and the only structural finding of
the audit.** `LocalProcess.init(delegate:dispatchQueue:)` accepts another queue and the view tests
`usesMainQueue` (`LocalProcess.swift:124–129`); what `AppleTerminalView` does when it is false has to
be read before anything is decided.

### U2 — The keystroke path scans the whole text three times, one of them twice

On every `didChangeText`:

- `CurrentLineTextView.rebuildLines()` (`Editor/CurrentLineTextView.swift:60–69`):
  `IndentGuides.levels(of: string, …)` bridges `NSTextStorage → String` (an O(n) copy), then
  `split(separator: "\n")` on `String` (grapheme-aware, n `Substring`s) and three `[Int?]` arrays
  (`ReadingAids.swift:26–59`); then `lineStarts(of:)` (`ReadingAids.swift:79–89`), a second scan.
- `LineNumberRulerView.rebuildLineStarts()` (`Editor/LineNumberRulerView.swift:188–200`), from the
  `NSText.didChangeNotification` observer: **the same `lineStarts` as `CurrentLineTextView`'s**, computed
  and stored a second time. `StickyLinesView` reads the text view's copy through a closure
  (`EditorTextView.swift:80`).
- 300 ms later, `EditorTab.refreshFolds` (`Editor/EditorTab.swift:268–280`) copies `currentText` on
  the main actor, then `Folding.structure` makes a new `Parser()` and parses the whole text
  (`Highlight/Folding.swift:37–38`) — off the main actor, but with no old tree and no `InputEdit`,
  next to Neon's own incremental parse of the same text. Back on the main actor, `setStructure`
  calls `rebuildLines()` again (`CurrentLineTextView.swift:49–58`).
- After `syncDelay`, the LSP is sent the whole text (`LSPServers.swift:90–104`, editor R37).

*Why it holds:* trivial code, no incremental state to desynchronise; editor R16 bounds n at 2 MB.
*Where it breaks:* files over ~500 KB, a few ms a keystroke. **ccoe: edited files are P50 3 KB,
P95 49 KB, P99 138 KB; the only files over 2 MB are SQL migrations, read-only by R16. At 50 KB all
of this is well under 1 ms. Only the duplicated `lineStarts` is worth removing; an incremental
parse is not.**

### U3 — `ensureLayout(for: documentRange)` lays out the whole document synchronously

At tab open (`Editor/EditorTextView.swift:120–122`) and after a format
(`Editor/EditorFeature.swift:612–614`). The comment says why (the clip view clamps the target
otherwise); the amount of layout asked for is not discussed — layout up to the target range would
do. **ccoe: at 50 KB this is invisible; closed by the numbers, kept on record.**

### U4 — Every `git status` rebuilds the explorer's outline from scratch

`runStatus` yields a `GitStatusChange` (`Git/GitFeature.swift:533–536`) →
`ExplorerModel.applyGitStatus` (`Explorer/ExplorerModel.swift:156–173`) refilters `gitStatuses`,
recomputes `propagate` (a joined `String` per ancestor per changed file, :181–192), then
`version += 1; lastLoaded = nil` → `ExplorerOutlineView.Coordinator.sync` sees `path == ""`,
calls `forgetItems()`, `reloadItem(nil, reloadChildren: true)` and a recursive `restoreExpansion`
(`Explorer/ExplorerOutlineView.swift:343–357`). An agent writing files produces an FSEvents batch
every 300 ms–1 s (`FSWatchService.swift:24`), hence a `status` and a full outline rebuild at that
rate, per repo, for the whole session. The same change also invalidates everything that reads
`GitModel.sections`, twice per status (`setLoading` on and off, `GitModel.swift:291–293`).

*Why it holds:* one path (`version`), stable items (explorer R10), no diff to write. *Where it
breaks:* a wide unfolded tree under an active agent. **ccoe: 2 002 files in scope, widest folder
181 entries, four repos watched — the rebuild is probably 1–2 ms, to be measured before acting
(M23 23.1); the consumer-side coalescing of K3 is the cheap fix if it is over.**

### U5 — Derived values recomputed per access or per `body`

- `ThemeService.tokens` is a computed property that rebuilds a whole `Tokens` (`applying(overrides)`:
  a copy of a ~30-field struct plus loops) **on every access** (`App/ThemeService.swift:92–94`,
  `ThemeService+Tokens.swift:184–199`). It is read several times per outline cell
  (`FileTree.swift:229–244`, `ExplorerOutlineView.swift:458–471`) and, above all, by
  `attributes(forCapture:)` → `color(for:)` → `tokens` **for every token Neon colours**
  (`Highlighter.swift:37`, `ThemeService.swift:161–169`): tens of thousands of reconstructions per
  highlight pass.
- `GitModel.groups` and `agentSessions(in:)` call `GitRepo.canonicalPath` →
  `resolvingSymlinksInPath()` → `realpath(2)` (`Git/GitRepo.swift:107–108`,
  `GitModel.swift:207–216, 251–262`) from the `body` of `GitChangesPanelView` (:32, 90). Syscalls
  in a body, on every evaluation.
- `GitModel.Section.sections` and `isCollapsed` rebuild `GitSections` on each read
  (`GitModel.swift:119–127`); `commitTarget` does it for every section.

*Why it holds:* nothing to invalidate, so nothing can be stale; `@Observable` tracks `overrides` and
`systemIsDark` for free. *Where it breaks:* the cost scales with call frequency, not data size — the
per-token case is the one that counts. **ccoe: independent of the workspace; worth fixing.**

### U6 — The layout snapshot is still serialised on every root body pass

`.onChange(of: layout.snapshot())` (`App/WorkspaceView.swift:155`) calls `snapshot()`, which runs
every tab kind's `serialize` (JSON) (`Layout/LayoutManager+State.swift:7–16`). This is the August
audit's M15, marked done in M17 17.10; the code on `main` still evaluates it per body. **Cheap to
fix; to confirm whether the dirty flag of 17.10 was lost or never landed.**

### U7 — Residual synchronous disk IO on the main actor

All of the order of one `stat`, harmless except on a network volume: `TerminalTab.isDirectory`
(`TerminalTab.swift:35, 84`), `isExecutableFile` at `launch` (`TerminalService.swift:224`) plus
SwiftTerm's own `forkpty`, `GitRepo.hasGitEntry` (`GitFeature.swift:81`, `AgentsFeature.swift:265`),
`ContentSearch.locateTool()` (~10 stats, `ContentSearch.swift:42–52`) evaluated as a default argument
in `SearchModel.init`, `GitCLI.resolveExecutable` inside a `Task {}` that inherits the main actor
(`GitFeature.swift:347–350`), `Workspace.init` → `existingFolder` + `migrateLegacyFolder`
(`Workspace.swift:54–55`). **Recorded, not scheduled.**

### Options weighed for the axis

| Option | UI latency | Memory | Cognitive debt | Verdict |
|---|---|---|---|---|
| Keep « MainActor by default, `@concurrent` for IO/parse » and fix U5, U6, the duplicated `lineStarts` | net gain on U2/U5/U6, none on U1 | none | very low: local edits, no new concept | the base, whatever else is decided |
| Give `LocalProcess` a dedicated serial queue (U1) | VT parse off the main thread; `updateDisplay` stays | none | medium: read what the view does when `usesMainQueue == false`, test on the agent TUIs | the one structural item; instruct before deciding |

## 3. Concurrency model

### What is well held

- `GitCLI` serialises writes with a hand-rolled lock (`isWriting` + `writeWaiters`,
  `Git/GitCLI.swift:186–202`); no `await` between test and take. Correct, 17 lines, no dependency.
- `LSPServer.ready()` shares one attempt through `starting` (`LSPServer.swift:105–118`); the comment
  at :27–31 records the reentrancy bug that was closed there.
- `Highlighter.configuration` caches the `Task`, not the result (`Highlighter.swift:65–78`): two views
  asking for the same grammar share one compile.
- `ExplorerModel.load` tests and inserts into `loading` before its first `await`
  (`ExplorerModel.swift:259–262`).
- `GitDiffModel.load`, `GitHistoryModel.load`, `SearchModel.search` cancel the previous task and
  check `Task.isCancelled` after every `await` before writing state.
- The fan-out streams are safe without back-pressure because producer and consumer share the main
  actor: the « buffer » is the actor's queue of turns, bounded by the upstream debounces.

### K1 — State read before an `await`, used after it

`GitFeature.runStatus` captures `section` then awaits three times and emits `section.repo`
(`GitFeature.swift:520–533`): a rediscovery in between leaves a stale `GitRepo` in the change (the
id does not move, so the impact is nil today). `ExplorerModel.resolveChain` reads `levels[last]`
after `await read(...)` (`ExplorerModel.swift:289–299`): a concurrent `forget()` can be undone by the
read that follows. Minor, recorded.

### K2 — Observable mutations without an equality test

`TerminalTab.didSetTitle` assigns `subtitle` unconditionally (`TerminalTab.swift:78–80`) where
`didResize` tests first (:48–51); `@Observable` notifies on `willSet`, so every identical OSC 0/2
re-renders the views reading it. `GitModel.update(id)` mutates `sections[index]` in place, so a
`setLoading` toggle invalidates the whole panel (`GitCommitView(sections: model.sections)`,
`GitChangesPanelView.swift:48`). Not bugs; avoidable re-renders.

### K3 — No coalescing on the consumer side of `statusChanges`

The producer is debounced (FSEvents); the consumer (`ExplorerModel.applyGitStatus`, U4) treats every
`GitStatusChange` although each one is a complete snapshot of its repo and only the last matters.
`AsyncStream(bufferingPolicy: .bufferingNewest(1))` on `statusChanges()` and `configChanges()` — and
**never** on `TerminalService.events()`, whose events are state transitions — removes the rafale at
one line a stream, at the documented price that intermediate snapshots are dropped.

### K4 — Small departures from the written rules

`Task.detached` in `ContentSearch.run` (`ContentSearch.swift:197`) carries no justification; the enum
is `nonisolated`, a plain `Task {}` there inherits no actor, so `detached` is unnecessary (not
harmful). `commitTasks` are retained and cancelled by `GitFeature`, `fetch`/`pull`/`push` are not
(`GitFeature.swift:601–770`): the criterion « which long tasks are retained » is applied but not
written down.

### K5 — Copy-on-write false friends

`SearchModel.add` does `var updated = groups` then `updated[index].matches.append`
(`SearchModel.swift:93–106`): `groups` still holds the storage, so each append copies that group's
`matches`. Bounded by 2 000 matches and 50 ms batches today; quadratic if the cap moves.

### Options weighed for the axis

| Option | UI latency | Memory | Cognitive debt |
|---|---|---|---|
| Keep: actors for IO, `@concurrent` for CPU, main for state, unbounded streams + producer debounce; fix K2, K4 | unchanged | unchanged | lowest, already documented |
| `Mutex` for shared model state | no gain: nothing reads it off the main actor | none | medium, and against the rule « no lock for business logic » |
| Consumer-side coalescing (K3), on status and config only | removes the rebuild rafale of U4 | none | low; document the dropped intermediates |

## 4. Memory footprint

### M1 — Terminal scrollback: the real bottleneck, and a deliberate one

`TerminalOptions(scrollback: 10_000)` per surface (`TerminalSurfaceView.swift:8, 20`). A
`BufferLine` is an array of `CharData` (~15 bytes a cell, `CharData.swift:189`) × columns; at 200
columns ≈ 3 KB a line, so **up to ~30 MB per full surface**, allocated lazily as output arrives. A
closed surface is kept ≤ 5 s (`closing`, `TerminalService.swift:176–184`); a restored idle tab has
no surface (`restore`, :93–98). **ccoe: three to five surfaces, ≤ 150 MB worst case — acceptable.
A `terminal.scrollback` key (R14 names « the size of the scrollback », which is a constant today)
is the only lever, and not a priority.**

### M2 — The diff is rendered whole, and held whole

`GitDiffModel.render` renders **every** file, expanded or not, and assigns `self.rendered` once at
the end (`Git/GitDiffModel.swift:176–190`). One `AttributedString` per line (shared between the two
sides of a context row); a « large » diff (git R16) is built entirely before anything shows, then
kept for files the user never unfolds. Transient on top: `highlighted`, an `AttributedString` of the
whole file (:183–185), and the `for run in string.runs` recolouring on the main actor
(`Highlighter.swift:57–61`).

*Why it holds:* one publication, no flicker. *Where it breaks:* a session diff of a few hundred
files. **ccoe: commit sizes as a proxy for agent sessions — P50 4–5 files / ~60 lines, P90 22–32
files / 750–2 250 lines, max 228 files / 22 000 lines (frontend). The P90 already trips the large
mode; the max freezes visibly. The best gain/effort of the audit: render the expanded files first,
publish `rendered[file.id]` as each completes, render a folded file when it is expanded.**

### M3 — Editor tabs keep their whole native stack

Per open tab: `FileDocument.text` + `NSTextStorage` (a copy) + Neon's tree + the `NSScrollView` /
`NSTextView` kept by `textCoordinator` (`EditorTab.swift:88`, editor R4). Transient per keystroke:
one or two `String` copies, a tree-sitter tree, the `levels` arrays. About **3× the file size
resident per tab, +2× at the peak of a keystroke**. **ccoe: at P95 49 KB this is nothing. Evicting
hidden tabs' native stacks would re-open onto U3; not recommended.**

### M4 — Bounded by specification, recorded for the orders of magnitude

`QuickOpenIndex` `[String: [UInt8]]` ≈ 100–150 B an entry → ~25–30 MB at the 200 000 cap
(`QuickOpenIndex.swift:8, 20`); **ccoe: 2 002 files, ~300 KB.** `ExplorerModel.levels` holds only
the folders read. `PipeIO.readToEnd` accumulates stdout in one `Data`, `GitOutput.text` decodes it
again on each access (`GitCLI.swift:9–11`): two transient copies. `SearchModel` is capped at 2 000
matches of ≤ 300 characters. `MarkdownImageCache` keeps decoded `NSImage`s for the life of a
preview (`MarkdownPreviewView.swift:290–317`). `Highlighter.configurations` holds one grammar per
language, by design.

### Options weighed for the axis

| Option | Memory | UI latency | Cognitive debt | Gain / effort |
|---|---|---|---|---|
| Keep, and write the orders of magnitude into `architecture.md` → Performance | unchanged | unchanged | none | the minimum: make the cost visible |
| Diff rendered per expanded file, published as it goes (M2) | −(folded files); peak per file, not cumulative | first hunk visible at once | low: the loop exists | **the best of the audit** |
| `terminal.scrollback` in the config (M1) | linear in the value | none | low (one key, `config.md`) | only if > 3 surfaces are common |
| Evict hidden editor tabs' native stacks (M3) | −2/3 per evicted tab | re-opening = U3 | medium-high, R4 to amend | not without a measurement; ccoe says no |
| One `lineStarts` shared by ruler, text view and sticky lines (U2) | −1 `[Int]` per tab | −1 scan a keystroke | low | small and free |

## 6. What this audit does not recommend

A dedicated `SerialExecutor`, a `Mutex` around model state, evicting editor tabs, an incremental
tree-sitter parse in `Folding`. The code has no contention problem; it has derived work repeated on
the main actor at a frequency the data does not justify (U4–U6), and a VT parser it did not choose
to put there (U1).
