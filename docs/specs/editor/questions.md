- [ ] **`.jsonc` is highlighted with the JSON grammar** (audit E8, 2026-08-30, `Language.swift`): a comment is not valid JSON, so every `//` line in a `.jsonc` file renders as an error. Three ways out — vendor a `jsonc` grammar, map the extension to no grammar so the file stays plain text, or teach the JSON grammar's query file to leave comments alone. A grammar decision, not a bug to fix in passing: to settle before touching the code.
- [ ] **A definition outside the workspace root** (2026-08-31, [03-study-lsp.md](03-study-lsp.md) R44): v1 refuses to open an SDK header, a `.swiftinterface` under `DerivedData` or a file in `node_modules`, and says where it is. Cheap and small-blast-radius, but for Swift it may well be the *common* case — jumping to a type of the standard library. To settle from use: leave it as is, or open such a target in a read-only tab, which restoration (R4), the disk watch (R9) and the explorer would all have to tolerate.

- [ ] **Two servers for one extension** (2026-08-31, [03-study-lsp.md](03-study-lsp.md) R35, edge cases): an Angular project wants `typescript-language-server` *and* `ngserver` on the same `.ts` — the first for TypeScript, the second for the Angular semantics of inline templates — which is what every editor with real Angular support runs. R35 maps one extension to one command, so v1 declares `typescript-language-server` on `.ts`/`.tsx`/`.js` and `ngserver` on `.html`: the templates keep their diagnostics, only the Angular part of the *inline* ones is lost. Accepting an array of commands per extension is backwards compatible (a string stays valid) but forces a policy — diagnostics concatenated from every server, and one owner to pick for hover and go-to-definition. To settle from use on a real Angular project, not before.
- [ ] **A server that asks for incremental sync gets full text anyway** (2026-08-31, task 18.1, [03-study-lsp.md](03-study-lsp.md) R37): `sourcekit-lsp` announces `textDocumentSync.change = 2` (incremental) and Foreman sends a single content change with no range, which is the *full* form. It works — sourcekit-lsp accepts it, verified against the real binary — and every editor that offers a "full sync" mode does the same, but it is a deviation from what the server asked for. To watch when the other three targeted servers are met: if one of them rejects it or drifts, R37's decision is what gets revisited, not the wiring.
- [ ] **A definition in a dependency is the common case, not the exception** (2026-08-31, task 18.2, [03-study-lsp.md](03-study-lsp.md) R44): checked against a real `sourcekit-lsp` on a SwiftPM package — jumping to a type of another module resolves into `.build/index-build/checkouts/…`, **outside the workspace root**, so R44 refuses it and shows a banner. R44 was written for the SDK header and the `.swiftinterface`, treating them as the edge; a dependency's own source is not an edge, it is where half the jumps go. Either R44 opens such a target read-only — restoration (R4), the disk watch (R9) and the explorer would each have to tolerate a path outside the root — or the banner has to be worth reading. To settle before M18 closes.
- [ ] **"No answer" and "cannot answer" look the same** (2026-08-31, task 18.2, R43): a `cmd+click` where the server has nothing to say does nothing, silently — the right behaviour for a click that misses. But a server that is *running and cannot answer at all* is indistinguishable from it, and that is not a corner case: `sourcekit-lsp` reads build settings from a `Package.swift` or a build server and cannot read an `.xcodeproj`, so on Foreman's own repository every jump returns `null` until `xcode-build-server` writes a `buildServer.json`. The author met exactly this and reasonably concluded the feature was broken. **Settled for this machine on 2026-08-31**: `brew install xcode-build-server` then `xcode-build-server config -project Foreman.xcodeproj -scheme Foreman`, with `build_root` pointed at the repository's own `DerivedData/` (the project builds there, `-derivedDataPath DerivedData`, not into the default one the tool finds); `buildServer.json` is gitignored, being absolute paths to one machine. The question stays open because the *product* answer does not follow from it: say something the first time a server answers `null` for a file, check for the marker files a server needs before offering the feature, or leave it and document it. Swift-only in practice — `typescript-language-server`, `ngserver` and `jdtls` read `tsconfig.json`, the Angular workspace and the Maven/Gradle model directly — which is why the author, the only one writing Swift here, is the only one who will hit it.
