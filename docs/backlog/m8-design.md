# M8 — Visual redesign

M8 = **choosing the look instead of putting up with it**: Wraith moves from the default system rendering (translucent materials, Liquid Glass, macOS chrome) to the **IntelliJ "Islands"** style in Dark — a flat dark ground, zones as rounded islands separated by gutters, a flat opaque toolbar, flat tabs, a single accent, no transparency. By the end of M8, the window looks like the mockup, and not a single view names a system color any more.

Domain covered: [`design`](../specs/design/) (transverse, no feature); every existing view is touched, along with `ThemeService` (`Wraith/App/ThemeService.swift`), which gains the tokens.

The **Library / native** column is mandatory (`AGENTS.md`). The **Tests** column: what is tested **and** what is validated by eye — most of M8 is rendering, which does not get a test (`coding-rules`: no view tests); each task therefore says explicitly what to look at.

## Verified before M8 (2026-08-27, on the code of `main` 2bf4f0e)

**`ThemeService`** (`Wraith/App/ThemeService.swift`) — what it exposes **today**, in full:

- `Settings` (the config's `terminal` section): `fontName: String?`, `fontSize: CGFloat` clamped to 8…32, `mode: .light/.dark/.system`; `Settings.decode(from: WorkspaceConfig)` with a per-field fallback.
- `settings`, `editorFont: NSFont`, `apply(_ config: WorkspaceConfig)` (called at startup and on every reload by `WorkspaceView`), `isDark(systemIsDark:)`, `font(for:)` (falling back to `monospacedSystemFont`).
- `TerminalPalette { foreground, background, cursor, selection, ansi: [NSColor] }` and `terminalPalette(dark:)`, with two static 16-color palettes.
- `attributes(forCapture: String)` and `color(for: HighlightRole) -> NSColor`, which return **system colors** (`.systemPurple`, `.systemRed`, `.secondaryLabelColor`, `.labelColor`…).

There is **no interface token at all**: no background, no radius, no gutter, no bar height, no accent. That is exactly what M8 adds — inside that type, not in a second service (design decision 2026-08-27).

`.bar` is a **translucent material**: exactly what `design` R1 forbids. It appears **eight times** (`WorkspaceView` ×2, `CenterView`, `ExplorerPanelView`, `EditorTabView` ×2, `TerminalTabView` ×2; `CenterView`'s is handled in 8.5, the seven others in 8.7).

**Window and toolbar**:

- `WorkspaceToolbar` (`Wraith/Layout/WorkspaceToolbar.swift`): an `NSToolbar` with `displayMode = .iconOnly`, `allowsUserCustomization = false`; `attach(to:)` does `window.toolbar = toolbar` then `window.toolbarStyle = .unified`, and **nothing else to the window** — no `titlebarAppearsTransparent`, no `backgroundColor`, no `titleVisibility`, no `.fullSizeContentView`. The items are `NSToolbarItem` / `NSMenuToolbarItem` with `isBordered = true` and a hand-composed `NSImage` for the badge (`WorkspaceToolbar.image(_:badge:)`, which already draws a colored dot in a corner).
- `WorkspaceView` (`Wraith/App/WorkspaceView.swift`) gives the window a `.navigationTitle(folder.lastPathComponent)`: that is the title `design` R14 wants hidden.
- `ZonesViewController` (`Wraith/Layout/ZonesViewController.swift`): two nested `NSSplitViewController`s, `splitView.dividerStyle = .thin` on both. That divider is what must become the gutter of `design` R2 and R20 — the thickness and color of an `NSSplitView` divider are controlled by subclassing `NSSplitView` (`dividerThickness`, `drawDivider(in:)`); to be checked on the machine, no build here.
- `CenterView` (`Wraith/Layout/CenterView.swift`) renders the split tree with `HStack`/`VStack` and SwiftUI `Divider()`s (M0 decision: pure SwiftUI, the center's splits are not resizable): the center's gutter is laid out there, not in `NSSplitView`.
- `TabBarView` (`CenterView.swift:78`) is already 30 pt tall and puts the active tab on `.controlBackgroundColor`: the height `design` R4 wants is the one that already exists.
- `PalettePanel` (`Wraith/Palette/Palette.swift`) is an `NSPanel` `[.titled, .fullSizeContentView, .nonactivatingPanel]` with `titleVisibility = .hidden` and `titlebarAppearsTransparent = true` — the palette already knows how to do without chrome; what it lacks is the opaque background, the radius and the shadow.
- `TerminalService.surface(for:)` (`Wraith/Terminal/TerminalService.swift:185`) creates the `TerminalSurfaceView` with `theme.editorFont`; `installColors` and `nativeBackgroundColor` are set from `terminalPalette(dark:)` (M2, `terminal` R14): the hook for `design` R13 exists, it just changes its source of colors.

**Config**: `WorkspaceConfig.section("theme", as:)` will work with nothing added (`config` R5: each feature decodes its section); `ThemeService.apply(_:)` is already called back hot by `WorkspaceView` on `configChanges()`. There is **nothing to wire** for reloading.

**SPM dependencies**: M8 adds none. The WCAG contrast computation is about fifteen lines; the `pbxproj` is not touched.

**Mockups**: eight scenes generated by the author on 2026-08-27 in `docs/specs/design/00-mockups/` (prompts in `00-mockups/mockup-prompts.md`), validated as inspiration with three rejections (`design/decisions.md`). The icon set for R23 is in `docs/specs/design/00-icons/` (Material Icon Theme, MIT, 1,192 SVG).

## What is waiting for another milestone

- A designed light theme, user theme files, a theme picker, a custom icon set, animations, support for "Increase contrast": out of scope for v1 (`design` 00-study).
- The user-theme question left by M2 (`m2-terminal-agents.md`, 2.6: "no user theme file in v1"): it lands here and **stays refused** — the config's `theme` section covers the need (design decision 2026-08-27).

## Definition of done (M8)

- `docs/specs/design/00-mockups/` is validated by the author, and the real window looks like it: the same ground, the same islands, the same gutter, one bar, the same accent; the three rejections of `design/decisions.md` (2026-08-27) are respected.
- **No transparency** in the window: `grep -rn "\.bar\b\|regularMaterial\|ultraThinMaterial\|NSVisualEffectView" Wraith/` returns nothing.
- **No color written inline**: `grep -rn "NSColor\.\|Color\.accentColor\|controlBackgroundColor" Wraith/` returns nothing outside `ThemeService.swift`.
- `.wraith/config.json` with `"theme": { "accent": "#4C8DF6" }` changes the accent everywhere, without a restart; an unknown key or an invalid color gives a warning and breaks nothing (`config` R7).
- `design` R7's contrast pairs are verified by a test over the `dark` set, not by eye.
- The terminal has no boundary against the island containing it; an agent TUI stays readable.
- Switching the macOS appearance mid-session repaints everything, SwiftTerm surfaces included.
- `cmd+opt+t`, the splits, panel resizing, full screen and size restoration work as before: M8 changes **no behaviour**, only the rendering.
- `xcodebuild test` stays green (the `layout`, `palette` and `terminal` tests are not supposed to move); lint clean; **no SPM dependency added**.
- `docs/specs/design` up to date; the domain's `questions.md` emptied (the toolbar route, the token values, the radius and gutter, the bar's background); if option B is chosen, `layout` R30 and `architecture.md` are amended and dated.

## To decide during M8 (decisions expected)

- 8.1: **the toolbar — a dressed `NSToolbar` (A) or a SwiftUI view (B)**? **Settled (2026-08-27, `design/decisions.md`): option A**, chosen by the author for the control it keeps over a native component. The comparison stays below as the record; B is the documented fallback if A leaves a material or separator that cannot be turned off.

  | | Option A — a dressed `NSToolbar` | Option B — a SwiftUI bar |
  |---|---|---|
  | What we write | 4 lines on `NSWindow` (`titlebarAppearsTransparent`, `backgroundColor`, `titleVisibility`, `.fullSizeContentView`), `toolbarStyle = .unifiedCompact`, `isBordered = false` and a view per item | ~150 lines: a view rendering the `ToolbarItemDescriptor`s, the inset for the traffic lights, window dragging, the hover states |
  | What we get | Very close to the target, but `NSToolbar` **exposes no background color**: how macOS paints its area (material, a separator when scrolling) is not contractual and may change with an update | Exactly the look we want, fully under control |
  | What we lose | Nothing | Item overflow, standard tooltips, customisation — all already forbidden by `layout` R30, so nothing in practice. But the traffic-light inset must be measured (~78 pt) **and re-measured in full screen** |
  | What it forces us to change in the specs | Nothing | `layout` R30 and `architecture.md` say "a native `NSToolbar` toolbar": to be amended and dated |
  | Risk | The appearance drifts with the next macOS version | A window case handled badly (full screen, a second display, dragging) |

  **Recorded proposal (accepted): start with A**, measure it on the machine with the mockup next to it, and move to B **only if** A leaves a visible material or separator that cannot be turned off. That is the "when hesitating between two solutions, take the shorter one" rule (`AGENTS.md`): A costs a few lines, B takes Wraith out of a native component that `architecture.md` P3 recommends. But the criterion is still the author's eye: if A does not give the mockup's look, B is legitimate and its spec is amended.
